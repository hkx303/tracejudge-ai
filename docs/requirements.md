# TraceJudge v1 需求基线

## 1. 目标

TraceJudge 是一个本地优先的 Web 工具，用于分析自动化测试失败日志，并基于可追溯证据将问题归因为产品/设备、测试工具、环境，或证据不足。系统不应把模型输出当作事实：日志片段是事实，归因和建议必须被标注为推断。

## 2. 用户流程

1. 用户上传一个或多个 `.log` / `.txt` 文件，为每个文件选择来源：测试工具、设备、产品服务或环境。
2. 用户可补充设备型号、产品版本和工具版本。
3. 系统解析日志、标准化事件、按时间和链路标识关联，执行规则评分和知识库检索。
4. 用户查看归因、置信度、时间线、日志证据、命中规则、知识库引用、反证与验证建议。
5. 用户可确认或更正归因、写入实际根因；确认后的记录成为可检索的历史案例。

## 3. 归因与输出

支持四个固定类别：

| 值 | 含义 |
| --- | --- |
| `PRODUCT_DEVICE` | 产品业务、服务、固件、设备硬件或设备配置问题 |
| `TEST_TOOL` | 测试脚本、自动化框架、驱动、解析、定位、超时或重试策略问题 |
| `ENVIRONMENT` | 网络、权限、供电、依赖服务或测试环境问题 |
| `UNKNOWN` | 证据不足；不得强行归因 |

每次分析返回：类别、0 到 1 的置信度、摘要、日志证据定位、规则命中、知识库片段、反证、验证动作、是否需人工审核，以及模型、提示词和知识库版本。

## 4. 分析链路

`文本日志 → 事件解析 → 时间线/链路关联 → 可解释规则评分 → RAG 检索 → 可选 OpenAI 增强结论 → 人工确认回写`

- 解析器支持有/无时间戳的普通文本，提取等级、错误码、异常栈、`traceId`、`requestId`、`sessionId`、`deviceId`。
- 关联优先使用链路字段，其次按时间排序；v1 不承诺跨机器时钟自动校准。
- 规则只产生分数和证据，不能替代最终审查。
- RAG 知识来自仓库中 Markdown：`knowledge-base/product`、`knowledge-base/test-tool`、`knowledge-base/cases`。只有 `verified: true` 的案例作为高可信案例。
- 配置 `OPENAI_API_KEY` 后使用 OpenAI 生成结构化增强结论；未配置时返回规则结论，并声明 `ai_status=not_configured`。

## 5. 接口与数据

- `POST /api/analyses`：multipart 上传日志与 JSON 元信息，创建并同步完成分析。
- `GET /api/analyses/{id}`：读取分析结果。
- `POST /api/analyses/{id}/confirmation`：保存人工确认；确认内容同时写入 SQLite 和知识库案例目录。
- `POST /api/knowledge/reindex`：重新读取仓库知识文档。
- SQLite 保存任务、原始日志（仅本地）、结果和确认记录；向量检索优先使用本地 Chroma，依赖不可用时使用内存关键词检索以保持本地演示可用。

## 6. 安全与质量

- OpenAI 密钥只能从环境变量读取，不写入代码、日志或数据库。
- 上传日志在持久化前脱敏常见 Token、Authorization 值、邮箱和手机号。
- 每个非 `UNKNOWN` 结论至少包含一条日志证据和一项验证动作。
- 原始日志和数据库默认仅存于本地 `backend/data`，生产部署前需另行定义权限、保留期限和对象存储。

## 7. 验收

- 可上传多份不同来源的日志并展示合并时间线。
- 样例覆盖产品/设备、工具、环境和证据不足，最后一类返回 `UNKNOWN`。
- 知识库结果可追溯到 Markdown 路径和文本片段。
- 未配置 OpenAI 时，界面和 API 清晰提示，仍提供规则分析。
- 人工确认会在后续相似查询中作为可检索案例出现。

## 9. 工程维护约定

- 后端按 `api`、`parsers`、`correlator`、`rules`、`rag`、`llm`、`persistence` 分层；模块间仅通过模型和明确接口协作。
- 文档分为需求、架构、API、数据模型和评测五类，任何变更须先更新需求文档和受影响的设计文档。
- 每次实现或需求修改完成后，必须进行适当验证，创建一个描述清晰的 Git 提交，并推送到配置的 GitHub 远程仓库。推送失败时要说明原因和待处理步骤。
